## 1. Overview

This feature implements the JWT verification middleware that protects backend API routes. When a request arrives with a `Bearer <token>` in the `Authorization` header, the middleware verifies the token, decodes the user ID, fetches the user from the database, and attaches it to `req.user`. If the token is missing, invalid, or expired, the middleware returns a `401 Unauthorized` response.

Once implemented, this middleware is applied to all transaction, category, and budget routes.

---

## 2. End Goal

When this feature is complete:

- The `protect` middleware verifies JWT tokens from the `Authorization` header.
- Verified requests have `req.user` populated with `{ id, email }`.
- Invalid/expired/missing tokens return `401` with a clear error message.
- All `/api/transactions`, `/api/categories`, and `/api/budget` routes are protected.
- `/api/auth/me` is protected.
- Public routes (`/api/auth/register`, `/api/auth/login`) remain unprotected.

## 3. Product Requirements (PRD)

### 3.1 Functional Requirements

| ID     | Requirement                                                                      |
|--------|----------------------------------------------------------------------------------|
| FR-001 | Middleware MUST extract the token from `Authorization: Bearer <token>` header.    |
| FR-002 | Middleware MUST return `401` with `"Not authorized — no token provided"` if header is missing or malformed. |
| FR-003 | Middleware MUST verify the token using `jwt.verify()` with `JWT_SECRET`.          |
| FR-004 | Middleware MUST decode the user ID from the token payload.                        |
| FR-005 | Middleware MUST query the database to confirm the user still exists.              |
| FR-006 | Middleware MUST return `401` with `"Not authorized — user not found"` if user was deleted. |
| FR-007 | Middleware MUST return `401` with `"Not authorized — invalid token"` for expired or tampered tokens. |
| FR-008 | Middleware MUST attach `{ id, email }` to `req.user` on success.                 |
| FR-009 | All `/api/transactions/*`, `/api/categories/*`, `/api/budget/*` routes MUST use this middleware. |

### 3.2 Non-Functional Requirements

| ID      | Requirement                                                                     |
|---------|---------------------------------------------------------------------------------|
| NFR-001 | Middleware MUST NOT log the token value (security).                              |
| NFR-002 | Error messages MUST NOT reveal whether the email exists or the token structure.  |

## 5. Detailed Implementation Steps

### Step 1 — Implement `protect` middleware (`server/src/middleware/auth.ts`)

The file already has the full structure scaffolded with commented code. Uncomment and complete:

1. Import `jwt` and the `User` model.
2. Extract the token from `req.headers.authorization`.
3. Verify with `jwt.verify(token, process.env.JWT_SECRET!)`.
4. Cast the decode result to `{ id: string }`.
5. Query `User.findById(decoded.id).select("-password")`.
6. If user not found, return 401.
7. Set `req.user = { id: user._id.toString(), email: user.email }`.
8. Call `next()`.

### Step 2 — Protect all routes

In each route file (`transactions.ts`, `categories.ts`, `budget.ts`):

1. Uncomment the import: `import { protect } from "../middleware/auth";`
2. Uncomment: `router.use(protect);`

In `auth.ts`:
1. Uncomment the import and change the `/me` route to use `protect`.
