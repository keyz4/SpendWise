## 1. Overview

Transactions are the core data entity in SpendWise. Every income or expense a user records is a transaction. This feature implements the full CRUD API — Create, Read (list + single), Update, Delete — with support for pagination, filtering by category/type/date range, and sorting.

---

## 2. End Goal

When this feature is complete:

- `GET /api/transactions` returns a paginated list of the authenticated user's transactions.
- Transactions can be filtered by `type` (income/expense), `category`, and `date range`.
- Transactions can be sorted by `date`, `amount`, or `createdAt`.
- `POST /api/transactions` creates a new transaction for the authenticated user.
- `PUT /api/transactions/:id` updates an existing transaction (only if owned by the user).
- `DELETE /api/transactions/:id` deletes a transaction (only if owned by the user).
- `GET /api/transactions/:id` returns a single transaction by ID.

## 3. Product Requirements (PRD)

### 3.1 Functional Requirements

| ID     | Requirement                                                                      |
|--------|----------------------------------------------------------------------------------|
| FR-001 | `GET /api/transactions` MUST only return transactions belonging to the authenticated user. |
| FR-002 | `GET /api/transactions` MUST support pagination via `?page=1&limit=10` query params (default: page 1, limit 10). |
| FR-003 | `GET /api/transactions` MUST support filtering via `?type=expense`, `?category=Food`, `?startDate=2025-01-01`, `?endDate=2025-03-31`. |
| FR-004 | `GET /api/transactions` MUST support sorting via `?sort=-date` (prefix `-` for descending, default: `-date`). |
| FR-005 | `GET /api/transactions` MUST return `{ transactions: [...], total, page, pages }` to support frontend pagination. |
| FR-006 | `POST /api/transactions` MUST accept `{ type, amount, category, description, date }`. |
| FR-007 | `POST /api/transactions` MUST automatically set `userId` to the authenticated user. |
| FR-008 | `POST /api/transactions` MUST validate that `type` is either `"income"` or `"expense"`. |
| FR-009 | `POST /api/transactions` MUST validate that `amount` is a positive number.       |
| FR-010 | `PUT /api/transactions/:id` MUST verify ownership before updating.               |
| FR-011 | `DELETE /api/transactions/:id` MUST verify ownership before deleting.            |
| FR-012 | `GET /api/transactions/:id` MUST return `404` if not found or not owned by user. |

## 5. Detailed Implementation Steps

### Step 1 — Add Index (`server/src/models/Transaction.ts`)

Uncomment:
```typescript
TransactionSchema.index({ userId: 1, date: -1 });
```

Optional — add a virtual for formatted amount.

### Step 2 — Implement `getTransactions`

1. Get `userId` from `req.user.id`.
2. Build a filter object: `{ userId }`.
3. Parse query params and add to filter:
   - If `req.query.type` → add `{ type: req.query.type }`.
   - If `req.query.category` → add `{ category: req.query.category }`.
   - If `req.query.startDate` or `req.query.endDate` → add `{ date: { $gte, $lte } }`.
4. Parse `page` (default 1) and `limit` (default 10) from query.
5. Parse `sort` (default `-date`).
6. Query with `.find(filter).sort(sort).skip((page-1)*limit).limit(limit)`.
7. Get total count with `.countDocuments(filter)`.
8. Return `{ transactions, total, page, pages: Math.ceil(total/limit) }`.

### Step 3 — Implement `getTransaction`

1. Find by ID and verify `userId` matches.
2. Return 404 if not found.

### Step 4 — Implement `createTransaction`

1. Validate required fields.
2. Create with `userId` from `req.user.id`.
3. Return `201` with created transaction.

### Step 5 — Implement `updateTransaction`

1. Find by ID, verify ownership.
2. Update only the provided fields.
3. Return updated transaction.

### Step 6 — Implement `deleteTransaction`

1. Find by ID, verify ownership.
2. Delete.
3. Return `{ message: "Transaction deleted" }`.
